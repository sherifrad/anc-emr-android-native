# Round 6b: one global delete / confirm / Undo mechanism (design spec, no code yet)
Owner requirement 2026-11-02: the delete + Undo + 8 s window + lock-clear behaviour built in 19c36fc / e8285ff for medications and lab results becomes ONE reusable mechanism. A new record kind (ultrasound, previous pregnancy, visit, delivery plan, attachment, ...) gets delete/confirm/undo by writing one small adapter and one registration line. No copy-paste per section (repo rule: one function per rule, call it, never copy). Risk level 3 (clinical data): frontier-tier review and independent test review for every round below. Paths relative to `app/src/main/java/com/sherifradwan/ancnative/` unless noted.

## 2. Target design
D620 Record type. New `enum class DeletableType` (MEDICATION, LAB, ULTRASOUND, ... one value per kind, in `storage/DeletableRecords.kt`). It replaces `DeletionKind`, the `UndoKind` kind part and the per-kind notices.
D621 Adapter interface (storage layer, one file per kind, ~40 lines each):
```
interface DeletableRecordAdapter<T : DeletableRecord> {   // DeletableRecord = { id, patientId, revision } on the Demo* models
  val type: DeletableType
  val fingerprintTag: String           // "MED", "LAB": keeps every existing fingerprint string byte-identical
  val deleteReceiptKind: String        // "MEDICATION_DELETE" etc: stored value, unchanged for med/lab
  val restoreReceiptKind: String
  val section: WorkspaceSection        // destination() after delete or restore
  val deletedNotice / restoredNotice / saveUndoneNotice: SavedNotice
  fun label(record: T): String         // text for the Undo bar (name only, never more clinical detail than today)
  fun canonical(record: T): String     // content string for the hash (same field order as the save fingerprint)
  suspend fun load(dao, id): T?        // row -> domain, null if absent
  suspend fun deleteRow(dao, id, patientId, expectedRevision): Int
  suspend fun insertRow(dao, record: T, revision: Long)
  fun record(patient: DemoPatient, id: String): T?   // in-memory lookup for the ViewModel
  val editorHook: EditorHook?          // see D625
}
```
`contentHash(record) = sha256(canonical(record))` is ONE function in `DeletableRecords.kt`; `medicationContentHash`/`labContentHash` become thin delegates kept for the existing save-path callers, then removed in the migration round once unused. Owning-patient check is not in the adapter: the repository compares `record.patientId` to the command once (generic).
D622 Registry. `object DeletableRegistry { fun <T> of(type): DeletableRecordAdapter<T> }` backed by a `Map<DeletableType, adapter>` built from a single list in one file; adding a kind = new adapter file + one list entry + one enum value. A unit test asserts every enum value is registered and every `fingerprintTag` and receipt kind is unique.
D623 Generic commands. `DeleteRecordCommand(type, editorSessionId="", operationUuid, patientId, expectedPatientRevision, recordId, expectedRecordRevision, deletedContentHash)` and `RestoreRecordCommand(type, operationUuid, patientId, expectedPatientRevision, record: DeletableRecord, sourceDelete: DeleteRecordCommand)`, both implementing `sealed interface RecordUndoCommand : ClinicalCommand { fun withPatientRevision(rev: Long): RecordUndoCommand }` (replaces the `when` at VM `:1176`). `recordKind` stays `ClinicalRecordKind`: the four existing values are kept; a new kind adds two enum values (the enum is a stored string, no DB constraint). Validity, fingerprint and `destination()/savedNotice()` come from the adapter: fingerprint is `"{tag}_DEL|op|pid|pRev|recordId|recordRev|hash"` and `"{tag}_RES|op|pid|pRev|" + sourceDelete.fingerprint + "|" + canonical(record)`, identical to D601/D602 text so receipts written by build 19c36fc still replay.
D624 Repository: ONE `deleteRecord(cmd)` and ONE `restoreRecord(cmd)` replace the four branches; both fetch the adapter from the registry and use only adapter methods plus the existing DAO queries and `deleteRestoreGuardFailure`. All D605/D606 rules, error codes, rollback-by-`ClinicalCommandAbort` and the D613 comment stay verbatim, in one place. `ClinicalDeleteRule.evaluateRestore(receipt, latest, existingRow, cmd)` loses its `when` (uses `cmd.type`, adapter tag and `contentHash`); its signature is unchanged, so `ClinicalDeleteRuleTest` keeps its call shape.
D625 State. `PendingDeletion(patientId, type, recordId)`; `UndoOffer(token, patientId, type, action: DELETE|SAVE, label, phase)` (these were already generic in shape; only the enums change; still no clinical payload beyond the label). Events collapse to `RequestDelete(patientId, type, recordId)` (replaces the two Request events); Cancel/Confirm/Committed/Failed/Undo* are unchanged. Editor-specific reducer code moves behind `EditorHook` (state package): `isOpenFor(state, recordId)`, `closeEditor(state, patientId): AncState`, `rebaseCreateDraft(state, patients): AncState`. Medication and lab hooks wrap today's `medicationDraft`/`labDraft` code (`AncState.kt:877-891`, `:910-927`); the reducer calls the hook through the registry, so no `if (kind == ...)` remains. The `SavedNotice` aliases (`:208-214`) are replaced by `adapter.deletedNotice` etc.
D626 `UndoCoordinator` (new `state/UndoCoordinator.kt`, plain class, no Android types) owns everything the ViewModel does now for Undo: `pending` token/command, 8000 ms timer (injectable `CoroutineScope` so tests use virtual time), restart-once (`MAX_UNDO_RESTARTS`), ambiguous replay of the exact command, STALE_PATIENT_REVISION retry after a fresh snapshot, stale-token no-op, newer offer replaces and finalises the older, lock/epoch clear and `sessionStillCurrent` check. Public surface: `beginDelete(type, patientId, recordId)`, `offerSaveUndo(type, patientId, recordId, receipt, savedRecord)`, `request(token)`, `clear()`. It talks to the outside through three lambdas only: `execute(cmd, epoch)`, `dispatch(AncEvent)`, `currentState()`. The ViewModel keeps one field and four delegating lines (`confirmDelete`, `requestUndo`, the post-save hook, `clearFrozenCommands`). `confirmDelete`'s two branches become one: find record via `adapter.record(...)`, build `DeleteRecordCommand` and the matching `RestoreRecordCommand`, run, arm the offer.
D627 Behaviour is frozen: every D610-D613 rule (dirty/archived/saving ignored, ConfirmDelete closes clean editor on same record, undo rebase, SubmitMedication* ignored while RUNNING, session epoch clear, 8 s then gone, one restart) is preserved bit for bit. Only the mechanism moves. No Room entity, DAO query signature, schema JSON or DB version changes (`app/schemas` untouched, S303 style check stays).
D628 Kinds that fit the adapter as is: medication, lab, ultrasound scan (has `revision`, table `ultrasound_scans`), previous pregnancy (`previous_pregnancies`), visit (`visits`), dating is NOT deletable (one row per patient, edit only). Delivery plan is added when its table/record exists (it needs a revision column; if it is a single row per patient it is edit-only like dating). Attachments are different (see D629).
D629 Attachments (`patient_attachments`, file on disk, no revision, deleted today by `VaultController.deleteAttachment` `:477`): need a two-phase adapter. Extra optional adapter members `val hasPayloadFile` + `suspend fun finalizeDelete(record)`: the row and receipt delete immediately, the encrypted file is shredded only when the Undo window closes (UndoExpired, second failure, replacement by a newer offer, or lock), and Restore is refused with RECORD_CONFLICT after finalize. This goes in its own later round and needs its own spec section because a lock must finalize (shred) rather than just forget. Until then attachments keep today's path.
D630 Hard rules for adapters: label shows the record name only (medication name, test name, scan date, pregnancy year); an adapter must not log or persist clinical text; the hash must cover every user-editable field and exclude `revision`; `canonical` order matches the kind's save fingerprint so a field added later fails the hash test.

## 5. Risks and review requirements
R1 A hash or fingerprint format drift silently breaks replay of receipts written by the current build and the restore guard (INVALID_COMMAND/RECORD_CONFLICT) -> golden-string tests (D652) and the 46-case DB test.
R2 Deleting clinical rows is irreversible after the window: any adapter that reports the wrong owner, revision or hash could delete another patient's or a stale row -> the repository compares patient and revision generically once; adapter tests must include cross-patient and stale cases per kind (DB test does).
R3 Timer/lock leakage: an offer or pending restore command holds a clinical record in memory; it must die at expiry, second failure, replacement and lock (`clear()` is called from `clearFrozenCommands`; test in `UndoCoordinatorTest`).
R4 Attachments hold files on disk (D629): a naive adapter would orphan or lose bytes; do not register until the two-phase design is reviewed.
R5 Backups taken before the delete still contain the row, receipts store a fingerprint only (D613 limits stay documented in one place).
R6 Shared mutable UI (one dialog/bar for the whole app): a second delete while an offer is open finalises the first (documented, tested).
Review: every round touching `app/src` (level-3 per AGENTS.md) needs a frontier-tier review plus an independent test review (the tests author differs from the core author). Reviewers get the diff, this spec and `check_r6b.py` output; vendors never receive patient data. Real-database DB test must be run on the emulator for R6b-1 and for every new adapter.

## Five most important decisions (summary)
1. D621/D622: one `DeletableRecordAdapter` per kind plus a single registry; adding a kind touches only its adapter, one list entry, one enum value.
2. D623/D624: generic `DeleteRecordCommand`/`RestoreRecordCommand` and exactly one `deleteRecord`/`restoreRecord` in the repository; fingerprint and receipt strings stay byte-identical, no Room schema or version change.
3. D626: `UndoCoordinator` owns timer, restart-once, ambiguous replay, stale-revision retry, replacement and lock clear; the ViewModel only delegates.
4. D625: generic `PendingDeletion/UndoOffer/RequestDelete` keyed by `DeletableType`; editor-specific closing and draft rebase move behind `EditorHook`.
5. D640-D643: one `DeleteConfirmDialog`, one app-level `UndoBarHost`, one 48 dp `DeleteIconButton`, strings defined once.
