# Round 6a: delete and undo for medications and lab results (logic round)
Owner decisions 2026-11-02: permanent delete after a confirmation dialog, then an Undo bar for about 8 seconds (afterwards gone for good). "Save and next" in the medication editor also offers Undo (removes only that medication). Applies to medications now and lab results with the same code path. UI (dialog, bar, delete buttons) is a separate design round; this round is model/state/storage only. Risk level 3 (data schema / clinical records): frontier-tier review and independent test review required.

## Items
D600 `ClinicalRecordKind`: add MEDICATION_DELETE, MEDICATION_RESTORE, LAB_DELETE, LAB_RESTORE.
D601 `DeleteMedicationCommand(editorSessionId="", operationUuid, patientId, expectedPatientRevision, medicationId, expectedMedicationRevision, deletedContentHash)`: recordId = medicationId; fingerprint "MED_DEL|op|pid|pRev|medId|medRev|hash"; valid only if uuid valid, ids non-blank, both revisions >= 1, hash is 64 hex chars.
D602 `RestoreMedicationCommand(operationUuid, patientId, expectedPatientRevision, record: DemoMedicationRecord, sourceDelete: DeleteMedicationCommand)`: recordId = record.id; fingerprint "MED_RES|op|pid|pRev|" + sourceDelete fingerprint + "|" + canonical(record).
D603 Lab twins `DeleteLabInvestigationCommand`, `RestoreLabInvestigationCommand` (prefixes LAB_DEL, LAB_RES).
D604 `medicationContentHash(DemoMedicationRecord)` and `labContentHash(DemoLabInvestigation)`: sha256 of a pipe-joined canonical string of every field except revision, same field order as the existing MED/LAB fingerprints. Changing any field changes the hash; the revision does not.
D605 Revision rules: record at revision r. Delete removes the row and writes a receipt with committedRevision r+1 (tombstone). Restore re-inserts the same id and fields with revision r+2. Reject REVISION_EXHAUSTED if r >= Long.MAX_VALUE-1.
D606 Repository `execute` gets four branches with the same guards as saveMedication (PATIENT_NOT_FOUND, PATIENT_ARCHIVED, STALE_PATIENT_REVISION, REVISION_EXHAUSTED). Delete: RECORD_NOT_FOUND if missing, CROSS_PATIENT_WRITE if another patient's, STALE_REVISION if hash differs or 0 rows deleted; then increment patient revision (abort if not 1) and write a MEDICATION_DELETE/LAB_DELETE receipt. Restore: source delete receipt must exist with kind, patient, record and fingerprint matching (else RECORD_CONFLICT); record hash must equal sourceDelete.deletedContentHash (else INVALID_COMMAND); the delete receipt must be the latest for that record (new `dao.latestClinicalReceiptForRecord`) and the row must be absent (else RECORD_CONFLICT); then insert with revision committed+1, increment patient revision, write a RESTORE receipt. Retrying a delete/restore is idempotent through the existing receipt replay.
D607 DAO: `deleteMedication(id, patientId, expectedRevision)`, `deleteLabInvestigation(...)` (DELETE ... WHERE id AND patient_id AND revision), `latestClinicalReceiptForRecord(patientId, recordId)` (ORDER BY committed_patient_revision DESC LIMIT 1). No Room schema change, no migration, DB version stays.
D608 `AncState`: `deleteConfirmation: PendingDeletion(patientId, kind MED|LAB, recordId)?` and `undoOffer: UndoOffer(token, patientId, kind DELETE_MED|DELETE_LAB|SAVE_MED, label, phase READY|RUNNING)?`. No clinical payload in AncState.
D609 Events: RequestDeleteMedication(patientId, medicationId), RequestDeleteLab(patientId, labId), CancelDelete, ConfirmDelete, DeleteCommitted, DeleteFailed, UndoRequested(token), UndoCommitted, UndoFailed, UndoExpired(token). New SavedNotice values MEDICATION_DELETED, LAB_DELETED, MEDICATION_RESTORED, LAB_RESTORED, MEDICATION_SAVE_UNDONE.
D610 ViewModel keeps private `pendingUndo` (command + token) and `undoJob` (delay 8000 ms, then UndoExpired(token) clears both); lives in viewModelScope. Delete and undo run through the same `controller.execute(cmd, sessionEpoch)` as other clinical commands and never touch an editor's savePhase. Vault lock clears them (`clearFrozenCommands`).
D611 After a chained save (SubmitMedicationAndAddAnother) commits, publish an UndoOffer of kind SAVE_MED (label = medication name) whose undo is a DeleteMedicationCommand for that medicationId (expectedMedicationRevision = the receipt's committed revision, hash built from the saved fields). Undo targets only that medication.
D612 Edge rules: RequestDelete is ignored for archived patients, while an editor has unsaved changes or `savePhase.blocksEditing()`; ConfirmDelete with a clean editor open on the same record closes it. Undo uses the current patient revision at tap time and retries once after a fresh snapshot on STALE_PATIENT_REVISION. After UndoCommitted the blank chained medication draft (create draft, same patient) is rebased to the new patient revision; while an undo is RUNNING SubmitMedication* is ignored. A newer offer replaces and finalises the older one. A stale/unknown token is a no-op.
D613 Documented limits (state in the code comment of the repository branch): receipts store a fingerprint, not content, so nothing clinical remains after the window; backups taken before the delete still contain the row; attachments linked to a deleted lab become unlinked (UI must treat a missing link as unlinked).
