**Round 3v review.** I read the full diff and both new source files and skimmed the tests. I did not run Gradle, so nothing below is test-verified.

**Hard Blockers:** none found.

**Should-fix**
1. **Failed debounce save is dropped (Q3).** `performSave` removes the record up front (`pendingRecords.remove(slot)`), and on failure it only does `lastSavedValues.remove(slot)`. Nothing is re-queued, so if the vault was briefly busy, the latest typing is not stored until the next keystroke. `flush()` on background then finds nothing pending. Fix: on failure, put the record back into pending (unless a newer one exists) so `flush()` retries it.
2. **Stale "saved" value after close.** In `onStateChanged`, `lastSavedValues.remove(closedSlot)` runs before the delete is queued. A save already in flight can still finish afterwards and set `lastSavedValues[slot]`. If the user reopens that slot and types the same text, `isSameAsSaved` suppresses the save even though the delete removed the row. Fix: clear `lastSavedValues` for the slot inside the delete's mutex block, after the delete.
3. **Lifecycle events reordered (Q4, Q111).** `onBackgrounded` and `manualLock` now run `controller.*` inside a launched coroutine after the flush. `onForegrounded()` is still synchronous. When a save is pending, the background call is delayed and a quick background→foreground can run as foreground→background. This also applies to `manualLock`. Fix: serialize the three lifecycle calls, or flush only when something is pending and call `controller` directly otherwise.
4. **Test-only shim in production code.** `DraftMapping.kt:10` declares `object VaultState { val Inspecting … fun Unlocked(…) … }`. It duplicates the storage `VaultState`, and the same file also imports the real one. The two test files use it and have no `VaultState` import. This violates rule 4. Remove the object and import `storage.VaultState` in the tests.
5. **Clean editors delete stored drafts (Q2).** `closedDraftSlot` returns the slot for any editor that was open, even a clean one (`val beforeSlot = activeDraftSlot(before) ?: return null` … `beforeSlot != afterSlot`). Opening an editor over a stored draft and cancelling without typing deletes the draft. This costs nothing today because there is no recovery UI yet. It will destroy recoverable text once step 3 exists. The spec's wording allows it, so confirm the intent with the owner. A safer rule is to delete only when `before` was dirty, or when the editor was closed by save or confirmed discard.
6. **Repeated slot rules (reuse principle).** The patient-id rule `baseRevision == null → NEW_PATIENT_DRAFT_KEY` is written in both `activeDraftSlot` and `draftRecordFor`. `DraftSlot(record.patientId, record.screenKind)` is rebuilt in `DraftAutosaver` three times. Fix: add a `DraftRecord.slot()` extension and have `draftRecordFor` derive its slot from `activeDraftSlot`.

**Nits**
- `manualLock` and `onBackgrounded` contain the same try / `withTimeoutOrNull(2000L)` / flush block. Extract one helper. `internal val autosaver` can be `private`.
- `flush()` and `performSave` catch `Throwable`, which also swallows `CancellationException`. After the 2 s timeout the loop still calls `store.save` for each remaining record. Each call fails immediately, so it ends quickly, but rethrowing cancellation is cleaner.
- Ultrasound: adding only images makes the editor dirty, so a draft with unchanged text fields is saved. This is harmless.
- A lock triggered by the controller's own timer (not `manualLock`) skips the flush. The collector then runs `cancelPending()`, so up to about 1 s of typing is lost. This is acceptable but undocumented.
- There is an untracked `retry/` directory at the repo root, and `.agents/TEST_MANIFEST.json` is modified. Neither is a spec file; check where they came from.

**Answers**
1. **Lock and kill:** lock is not treated as discard. `closedDraftSlot` returns null unless both states are Unlocked. The collector's reset calls `_state.value =` directly, never `onStateChanged`, then `cancelPending()`. Nothing is deleted. Background and `manualLock` flush first. A hard kill loses at most about 1 s plus whatever failed in point 1.
2. **Removal on close:** every path goes through `updateState` and `AncReducer` (save, cancel, confirmed discard), so removal looks correct for all nine screens. A new patient uses the `NEW_PATIENT_DRAFT_KEY` slot. Lab and medication "save and add another" close the old editor in `RecordCommitted`, which deletes the draft. The chained `StartLabEditor` / `StartMedicationEditor` then opens a new clean editor through `dispatch`. The showDiscardDialog state alone doesn't delete.
3. **Typing order:** I found no way for an older value to overwrite a newer one. `saveMutex` is FIFO, all calls run on Main, and the take-record-then-lock step has no suspension point. The debounce restart is correct. The flaws are points 1 and 2. Saving while the vault is locked is safe because `saveDraft` returns false when the session is null, under `storageMutex`.
4. **Flush before lock:** `withTimeoutOrNull(2000L)` plus try/catch means the lock always happens, even if the write hangs or throws. Point 3 is the one caveat.
5. **Storage and logging:** the draft goes only through `controller.saveDraft`, which writes to the encrypted repository. There is no Log, SharedPreferences or File use, and `EncryptedBackupManager` is untouched.
6. **`applyDraftRecord`:** it sets a new `editorSessionId` (UUID), clears errors, and keeps ids, revisions, `original` and `imageUris` from the fresh editor. Missing fields keep the editor's values, and a non-matching slot returns the state unchanged. `draftRecordFor` covers every field in the nine value classes.
7. **State changes:** every `_state` write goes through `updateState`, including the save-result handlers. The only exceptions are the collector's patients-only update (draft untouched) and the lock reset, which is deliberately not reported.
8. **Scope:** no UI files changed. Apart from the `VaultState` shim (point 4) and the duplication (point 6), I found no unrequested features or dead code.
9. **Tests:** they call production code and would fail to compile on the old code. They cover mapping for all nine screens, the debounce, flush, close and lock. Nothing tests the ViewModel wiring, the 2 s timeout, or the failed-save retry (point 1). I recommend adding tests for the failed-save retry and the in-flight-save-then-close race (point 2).
