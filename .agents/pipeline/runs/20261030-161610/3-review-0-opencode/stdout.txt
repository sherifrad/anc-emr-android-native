### NEW DEFECTS FOUND (by severity)

#### HARD BLOCKER
1. **Lockout StateFlow staleness** (Q27e): `SecuritySettingsRepository.lockoutRemainingMs` StateFlow only updates via explicit `refreshLockout()` calls. When lockout expires naturally (app in background, user returns after lockout), `settingsState.lockoutRemainingMs` remains >0 until next PIN attempt or Settings dialog open. The lock screen polls every second so it's OK there, but any other UI reading this value (Settings dialog, future screens) shows incorrect lockout time.

2. **Legacy PIN "123456" check uses list join** (SecuritySettingsRepository line 98): `pin == listOf('1', '2', '3', '4', '5', '6').joinToString("")` — works but brittle; should use string literal "123456" for clarity (the check is only for migration logic, not a default).

3. **Process death + restore scenario**: On cold start, `isAppLocked = configured` (true if PIN exists). But `lastUnlockedAt = 0L` means `shouldLockOnBackground` would return true for IMMEDIATELY timeout, though `lockApp()` is idempotent. OK.

#### SHOULD-FIX
4. **Biometric prompt on lock screen auto-launches** (AppLockScreen LaunchedEffect): Auto-triggers biometric on first show if enabled. If user cancels biometric, `errorMessage` shows "Fingerprint verification failed. Use your PIN." but `onResult(false)` doesn't set lockout. Acceptable but could be clearer.

5. **Settings dialog biometric Switch enabled state**: `enabled = isBiometricAvailable` — correct. But when disabled, the switch is grayed out; user can't toggle. Good.

6. **Settings dialog "Change PIN" doesn't verify current PIN**: ChangePinDialog only validates new PIN via `isValidNewPin`, calls `securityRepo.updatePin(newPin)` which stores v2 hash without verifying old PIN. Spec Q27(h) says "updatePin rejects anything isValidNewPin rejects" — doesn't require current PIN verification, but this allows PIN change without knowing current PIN if Settings is accessible. **However**: Settings is only accessible when app is unlocked, so user already authenticated. Acceptable.

7. **BiometricAuthManager promptBiometric onResult(false) on cancel**: Returns false for both failure and cancel. AppLockScreen treats both as "Fingerprint verification failed. Use your PIN." — doesn't distinguish cancel vs fail. Acceptable per spec.

#### NIT
8. **strings.xml pin_lockout format**: Uses `%1$d:%2$02d` (minutes:seconds) but spec says "Try again in <time>." — format acceptable.

9. **AppLockScreen LaunchedEffect for biometric auto-launch**: Runs when `setupMode`, `legacyChangeRequired`, `isBiometricEnabled`, `isBiometricSupported` change. If user enables biometric in Settings while lock screen showing, it won't re-trigger (biometricAttemptedOnLaunch stays true). Minor.

10. **SecuritySettingsRepository.legacyHashPin uses "ANC_CLINIC_SALT_v1_"** — hardcoded salt. Only used for legacy migration check. Acceptable.
