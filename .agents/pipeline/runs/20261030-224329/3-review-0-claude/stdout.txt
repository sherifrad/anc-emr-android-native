Review of Round 3f-3 (read-only, nothing was run). The two Hard Blockers share one cause: a flag that is read in `onDispose` is never updated, because the dialog that owns it is removed before it recomposes.

**Hard Blockers**

1. **"Use photo" can delete the photo it just handed over.** `InAppCameraDialog.kt:110-120` reads `latestCommitted by rememberUpdatedState(committed)` inside `onDispose`.
   - The "Use photo" click sets `committed = true` (line 246) and calls `onCaptured`. That callback sets `showCamera = false` in `AddAttachmentDialog` and `UltrasoundEditor`.
   - The parent recomposes first and drops the dialog. The child scope never recomposes, so `rememberUpdatedState` never picks up `true`.
   - `onDispose` then sees `latestCommitted == false` and runs `deleteIfCaptureTemp(...)` on the file just committed.
   - In `UltrasoundEditor` the draft IMAGE_URIS entry would point at a deleted file. In `AddAttachmentDialog`, `selectedUri` would point at one.
   - Fix: keep the flag in a plain field, for example `session.committed = true` (the `CameraSession` class already exists), and read that field in `onDispose`.
   - I'm confident from the Compose recomposition order, but it was not run. Check on a device.

2. **Saving can delete the photo before the vault reads it.** `AddAttachmentDialog.kt:94-103` has the same pattern with `latestSent`.
   - Save sets `sent = true` (around line 384), calls `onSave`, then `onDismiss()`. The dialog is removed without recomposing, so `latestSent` stays `false`.
   - `onDispose` runs `deleteIfCaptureTemp(context, pending)` while the view model's IO coroutine is still reading `sourceUri`.
   - Result: intermittent `SAVE_FAILED` for camera photos only. Gallery URIs are ignored by the helper.
   - Fix: use a non-snapshot holder, as in blocker 1.

**Should-fix**

3. **Orphaned camera temp when the user then picks from the gallery.** The `photoPickerLauncher` callback (`AddAttachmentDialog.kt:89-91`) does `selectedUri = uri` without deleting the previous camera temp. Only the final `selectedUri` is cleaned in `onDispose`. A plaintext clinical photo stays in `cache/camera`. Call `deleteIfCaptureTemp(old)` there, the same way the camera `onCaptured` does.

4. **Q58 not implemented: `clearStaleCaptures(context, 24h)` is not called when the camera opens.**
   - The `CameraCaptureHelper.kt` KDoc says this is deliberate, because saved scan photos still live in `cacheDir/camera`. That reasoning is sound, and calling it would delete clinical photos.
   - But then crash leftovers (temp files from a process kill) are never cleaned, and `clearStaleCaptures` is dead code. This breaks the "no speculative abstractions" rule.
   - The spec author needs to decide: drop the function, or move scan photos out of the cache first. Until then this is a spec deviation, not a bug.

5. **Stale error banner.** `takePhoto()` (`InAppCameraDialog.kt:158-162`) does not reset `failed`. After one failure, the "photo could not be taken" text stays visible while the next capture runs. Set `failed = false` when capture starts.

**Nit**

6. **Possible dangling view.** `session.previewView` keeps a detached `PreviewView` after Retake until the new factory call overwrites it. If the bind listener ran before the factory, `checkNotNull` would set `bindFailed`. This is unlikely, but a one-line comment or a null reset in `onDispose` would settle it.

7. **Tests only cover the enum.** `PhotoQualityPresetTest` exercises production `PhotoQualityPreset` and covers the values, the default, and `defaultFor`, including the `"ultrasound"` lowercase and `""` cases. It does not test `deleteIfCaptureTemp` (traversal, symlink, foreign authority) or that the preset reaches the vault. Both need Robolectric or instrumentation and are not present. `exifTransform` tests were not in the files I read.

**Your six questions**

1. **Camera release and error handling.**
   - `unbindAll` runs in `onDispose` and is guarded by `disposed`, so a late listener does nothing.
   - The capture callbacks check `session.gone`. `onImageSaved` deletes the file if it lands after dismissal, and `onError` deletes it and shows `camera_capture_failed`. Retake and Close delete the temp file, except for the blocker 1 flag.
   - Permission denied shows the message and Close, with no crash.
   - Main thread: only `mkdirs`, `uriFor` and small deletes run there. The decode runs on `Dispatchers.Default`.
2. **Result flow.** It matches the old TakePicture path (`selectedUri`, draft IMAGE_URIS), apart from blockers 1 and 2. The extra delete of the old camera temp in `onCaptured` is fine.
3. **Presets.** The values match the spec exactly: SMALL 1280/70, STANDARD 1600/75, DETAILED 1920/85. `defaultFor` gives ULTRASOUND → DETAILED and everything else → SMALL. The path is `onSave(..., preset)` → `AncEvent.AddAttachment(preset)` → `AncViewModel` passes `preset = event.preset` → `saveAttachment` → `compressAndWrite` uses `preset.maxSide` and `preset.webpQuality`. The old constants are removed.
4. **`deleteIfCaptureTemp`.**
   - **Path traversal and symlinks:** it requires the scheme, the authority and `segments[0] == "camera_photos"`. It canonicalizes both root and candidate and requires `candidate.parentFile == root`. `..` segments, `%2F`, subfolders and symlinks pointing outside all return false.
   - **UltrasoundEditor drafts:** only the view model's `AddAttachment` path deletes, so these URIs are only at risk from blocker 1, not from the helper.
5. **Duplicated rules.** I found none. `createCameraTempUri` reuses `createCameraTempFile`. The still decode uses `BoundedBitmap` and `InAppCameraDialog` has no EXIF code. The 1280/1600/1920 and 70/75/85 numbers live only in the enum. `STILL_MAX_SIDE = 1600` in the dialog is a separate constant, but it duplicates `STANDARD.maxSide` only in value.
6. **Tests.** See Nit 7.
