**Coverage by D item:**
- **Commands (medication and lab twins):**
  - Validity: revision 0, blank ids, bad uuid, and bad hash (short, long, non-hex).
  - Fingerprints: restore fingerprints are tested against each field plus the source delete, and delete fingerprints against each of their fields.
  - Content hash: ignores `revision` but changes with every other field, for both medication and lab.
- **`ClinicalDeleteRule.evaluateRestore`:** returns `RECORD_CONFLICT` for a wrong kind, patient, record or fingerprint, a receipt that isn't the latest, or a row already present. It returns `INVALID_COMMAND` for a hash mismatch. Success returns null, and a revision-only difference still succeeds. It also has a lab case.
- **State:**
  - Delete requests are ignored for an archived patient, a dirty draft, or `savePhase` PENDING/RECONCILING/UNRESOLVED. A clean state does ask for confirmation.
  - `CancelDelete` drops the confirmation.
  - `ConfirmDelete` closes a clean editor on the same record and leaves one on another record open.
  - A stale token is a no-op for both `UndoExpired` and `UndoRequested`, and a matching `UndoRequested` moves the offer to RUNNING.
  - `UndoCommitted` rebases the blank create draft to the new patient revision.
  - A newer offer replaces the older one.

**Assumptions (the spec gives no signatures for these; fix them in one place if the core lane differs):**
- Names: `UndoOffer(token: String, patientId, kind: UndoKind.DELETE_MED, label, phase: UndoPhase.READY/RUNNING)`.
- Events: `UndoCommitted(patients)` and `DeleteCommitted(patients, offer)`.
- `ClinicalDeleteRule.evaluateRestore` is called with non-null receipts and a medication or lab record as the existing row.
- After `UndoCommitted`, `undoOffer` is expected to be null.

**Weak spots:**
- `submitMedicationIgnoredWhileUndoRunning` is trivially true at reducer level, because Submit events already return the state unchanged. The real guard lives in the ViewModel, which I can't unit-test without extra scaffolding.
- `lockResetClearsUndoOffer` only checks that a fresh `AncState` has no offer or confirmation. That is what the ViewModel builds on lock, but it doesn't exercise `clearFrozenCommands`.
- "success revision = tombstone+1" is a repository concern, not part of the pure guard, so it isn't tested here. It belongs in the instrumented test.
