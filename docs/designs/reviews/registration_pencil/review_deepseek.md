**1. VERDICT: PASS**

The pure function, its four call sites, and the reducer's Begin path all match the spec. I found no state that lets an archived patient into an editor, no path where the chip starts both the flow and the workspace, and no way for the attention dialog to start a flow. The findings below are integration/UX defects around the new chip, not spec violations.

**2. Findings**

- **moderate — `app/src/main/java/com/sherifradwan/ancnative/ui/patientdirectory/PatientDirectoryCard.kt:87-108` (and the same class of problem at `PatientActionsModalSheet.kt:169-175`)**: an archived patient that was archived *mid-registration* (`status == "archived"`, `ageText == null` or `dating == null`) still has `row.isIncomplete == true`, so the card renders a fully enabled, clickable "Continue registration" chip (and the sheet renders an enabled "Edit demographics" row). Tapping either calls `editPatientEvent`, which returns null at `PatientEditEntry.kt:17`, so `?.let(onEvent)` does nothing: no navigation, no dialog, no disabled state, no explanation. The control is a dead affordance. The chip's visibility should be gated on `status != "archived"` (or the control should be disabled/hidden), not just on `row.isIncomplete`.

- **moderate, conditional on the helper's implementation — `PatientDirectoryCard.kt:87-99`**: the chip uses `Modifier.minimumTouchTarget().clickable { ... }`, i.e. the size helper is *outside* the pointer-input node. That is correct if `minimumTouchTarget()` applies a minimum size to its child (e.g. `sizeIn(minWidth = 48.dp, minHeight = 48.dp)`), because the clickable child is then measured at 48 dp. It is wrong if the helper is layout-based (measures the child at its natural size and then reports a larger size, the way `minimumInteractiveComponentSize()` does): the clickable node then keeps the badge's own height (~24 dp), and the rest of the 48 dp box is dead space whose taps fall through to the card's own clickable. Concrete failure in that case: on a 360 dp card, a tap in the lower half of the "48 dp" target opens the patient workspace instead of resuming registration — which is exactly the double-trigger behaviour the spec is worried about, and the 48 dp requirement silently unmet. This needs the body of `minimumTouchTarget()` checked before the finding is closed.

- **minor — `RegistrationFlowDriver.kt:97-103` used from the new directory entry point**: `exitFlow` unconditionally sets `route = AncRoute.Workspace(patientId)`. New scenario created by the chip: the doctor taps "Continue registration" on a card in the *directory* (the chip's `Begin` is accepted, `startFlowEditor` opens the step), then backs out of the flow (system Back at a step whose flow Back is `FlowResult.Exit` goes through `requestBack`, or the flow completes). He is deposited in that patient's workspace, a screen he never opened, instead of back on the list he started from. Same for a flow that exits after the last step. The pencil path is unaffected because it already starts from the workspace.

- **minor — `PatientEditEntry.kt:19-26` combined with `RegistrationFlowDriver.kt:125-132`**: the chip and pencil are the only two entry points where a user-visible control can end in a completely silent no-op. `beginFlow` returns `state` unchanged when `registrationFlow != null`, when `deriveStepStatuses(patient).values.all { it == DONE }`, when the patient is missing/archived, and when `startFlowEditor` refuses (dirty draft / `savePhase.blocksEditing()`); `startFlowEditor`'s own refusal (`started === state`) does the same. None of these produce a dialog, a toast, or a disabled control, while the *complete*-patient branch of the same control always opens the editor. I could not construct a reachable stale-flow state (see check 2 below, the `withFlowConsistent` post-pass clears it), so this is a latent trap rather than a reproducible bug — but for the `hasDirtyDraft` and "all steps done" cases the user gets a button that does nothing.

**Answers to the specific checks**

- *Can the chip tap also trigger the card's own click?* No. The chip's `clickable` is a descendant of the card's clickable node; Compose dispatches the pointer to the innermost hit node and `detectTapGestures` consumes the gesture there, so the card's tap detector is cancelled. The only way the card fires is the dead-ring case in finding 2, where the tap misses the chip's (badge-sized) pointer node entirely.
- *Does a state with a stale `registrationFlow` block Begin?* `beginFlow` (line 126) does block it and returns the state unchanged, but I could not make it reachable: `withFlowConsistent` (210-218) clears the flow on the first event after the route stops matching a flow step or the active editor session stops matching, and every route change to the directory or workspace goes through the reducer. So by the time the chip or pencil is tappable, `registrationFlow` is null. It is untested defensive code, and Begin is dropped without feedback if it ever does fire.
- *Does the attention dialog on an incomplete patient still save?* Yes, unchanged. It sends `AncEvent.StartPatientEditor` directly (never `editPatientEvent`), then the draft change, then `SubmitPatientProfile`; `registrationFlow` is null on the workspace route, so `forcesAgeRequired()` is false and `reduceRegistrationNext` is not involved. Nothing in this diff reroutes it. (It still saves without the flow's identity requirements — pre-existing, not introduced here.)
- *Does anything let an archived patient into an editor?* No path added by this diff. `editPatientEvent` blocks at line 17, and `beginFlow` (127) and `openCountPrompt` (88) re-check `status != "archived"` independently. The only unguarded way in remains a direct `AncEvent.StartPatientEditor` from UI outside these four call sites (the attention dialog), which is not reachable for an archived patient.

**3. Test gaps**

- No test proves the four UI call sites actually go through `editPatientEvent`. A regression that reintroduces a literal `AncEvent.StartPatientEditor(...)` in `PatientActionsModalSheet`, `PatientHubScreen`, `OverviewTab` or the chip would keep the suite green.
- No test for the invariant the spec calls out explicitly: attention-dialog path `StartPatientEditor` → draft change → `SubmitPatientProfile` leaves `registrationFlow == null` and the save lands.
- No test that the flow survives the *next* event after a Begin. `reducing_incomplete_event_sets_registration_flow` asserts the state immediately after the Begin only; it does not send a following `DraftChanged`/`RegistrationNext`, so nothing proves `activeEditorSessionId` really equals `flow.activeEditorSessionId` and that `withFlowConsistent` keeps the flow alive. This is the one place where a directory-origin Begin could diverge (e.g. draft recovery reassigning the session id would wipe the flow on the next event and make Next a no-op).
- Begin from the directory route is only exercised for DATING. IDENTITY and OBSTETRIC (both routed through `startPatientEditor`/`PatientEditor`), HISTORIES, and PREGNANCIES (count-prompt path, where `startFlowEditor` sets `activeEditorSessionId = null`) are untested from a non-workspace route.
- No test that Begin is refused when `registrationFlow != null`, when the drafts are dirty, or when `savePhase.blocksEditing()` — i.e. the silent-no-op cases in finding 4.
- No test that `beginFlow`'s own archived guard holds, as distinct from the helper returning null (a stale `patient` snapshot in a card is the only way to reach it, but the guard deserves a test since it is the reducer-level defence).
- No test of the `firstNotDoneStep(patient) ?: IDENTITY` fallback: a patient where `isRegistrationIncomplete` is true but no step is reported missing is untested, and that combination is exactly what would make `beginFlow` drop the Begin when `deriveStepStatuses` reports all DONE.
- No test for the archived-and-incomplete card (finding 1), and no Compose test asserting the chip does not open the workspace / meets 48 dp.
