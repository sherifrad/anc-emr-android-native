## What this proposes

The Overview tab of a patient chart in an Android antenatal-care app currently shows six stacked cards. Several of them repeat data that the always-visible header already shows, and the past-pregnancy cards make the page very long. The document proposes replacing the cards with one continuous surface. It has titled sections separated by thin dividers, each section wrapped in a new container composable, `ClinicalGroupSection`. Past deliveries become compact two-line rows. GA at delivery and birth weight are pulled out of existing free-text fields with regular expressions, because the database schema is frozen. The redundant GA display is removed from the body. Edit, delete and add controls get touch targets of at least 48dp. The work is a file-by-file plan: one parsing helper with tests, three new component files, a refactor of `OverviewTab.kt`, new strings, and verification on a physical device.

## How the existing system works, per this document

`OverviewTab` sits below `PatientHubHeader`, which always shows GA, EDD, age, G/P, blood group, allergies and attention flags. Below the header, `OverviewTab` stacks `GestationalDatingCard`, `ObstetricParityCard`, `MedicalHistoriesCard`, one `PreviousPregnancyCard` per prior delivery, `DeliveryPlanningCard` and `AttachmentsSectionCard`. Each card has its own border, tint and elevation. GA at delivery and birth weight apparently have no dedicated fields. The document says they can be found in free-text `otherDetails` and `outcomeText` fields on a prior pregnancy. Patient data comes from a `patient` object, and the delivery plan comes from a `parsed` object. The document does not say how `parsed` is produced or what it parses.

2. 🔴 **Blocker.** Scope: Section 4.4 against Section 6.1 item 1. The regexes may extract wrong clinical values, and the document does not address this. The document calls the extraction "safe" and "non-destructive". Its GA pattern, `\d{1,2}(?:\+\d)?\s*(?:w|wks|weeks?)`, matches any text like "2 weeks" or "6w" anywhere in free text. That includes "induced at 6w postpartum" and "admitted 2 weeks before delivery". The weight pattern would match `3 kg` from other contexts. The first match is shown as the delivery GA or weight in a clinical safety context. The document names no rule for choosing between several matches and no handling for ambiguity.
   - The display example is `GA 39w 2d`, but the regex captures only the `w` part (`39w`). It would drop `2d`. A bare `\b` before the number also fails for a `+` form like `39+2`.
   - Section 6.1 tests `39w` while Section 6.2 tests `39w 2d`, so the specified test input does not match the example in Section 4.3.
   - Not explained: how the "clean `—` fallback" differs from a wrong value shown with confidence.
